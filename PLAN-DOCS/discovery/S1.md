# S1 — Nested tools not parsed/recognized for credential assignment: root-cause brief

Discovery only (2026-08-01, branch `phase4-builder-harness`). No source changed. All
file:line references verified by reading the code in this pass, not from memory.

---

## 0. DIAGNOSIS FIRST — is nested-ness the cause? **No.**

The backlog framing ("nested tools not parsed/recognized") is a misattribution.
Every layer that parses, detects, or injects credentials handles nested tools
correctly. The comparison across the three surfaces:

| Layer                                                                                                                      | Nested tool (WebSearchTool → internal FirecrawlBubble; agent tool)                                                                                                                                                                                                                                                                                                                                                                                                                                      | Direct service bubble (GoogleDriveBubble)                    |
| -------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| Detection (`extractRequiredCredentials`)                                                                                   | INCLUDED — bubble-level via `BUBBLE_CREDENTIAL_OPTIONS['web-search-tool']`, and agent tool-level via `extractToolCredentials` (`apps/bubblelab-api/src/services/bubble-flow-parser.ts:695-701` + `:719-787`); the SYSTEM filter is commented out (`:705-707`)                                                                                                                                                                                                                                           | INCLUDED (same path)                                         |
| Runtime injection (`BubbleInjector.injectCredentials`)                                                                     | INCLUDED — ai-agent bubbles union tool-level + capability-level cred types into `allCredentialOptions` (`packages/bubble-runtime/src/injection/BubbleInjector.ts:498-518`); AIAgentBubble forwards its `params.credentials` per tool via `BUBBLE_CREDENTIAL_OPTIONS` lookup (`packages/bubble-core/src/bubbles/service-bubble/ai-agent.ts:1271-1296`); WebSearchTool passes `credentials` into its nested `FirecrawlBubble` (`packages/bubble-core/src/bubbles/tool-bubble/web-search-tool.ts:130-141`) | INCLUDED (plain `BUBBLE_CREDENTIAL_OPTIONS['google-drive']`) |
| Binding surfaces (Setup tab, node dropdown auto-default, studio auto-bind, server auto-bind/heal, run-blocking validation) | **SKIPPED — because `FIRECRAWL_API_KEY ∈ SYSTEM_CREDENTIALS`**, not because it is nested                                                                                                                                                                                                                                                                                                                                                                                                                | Served — because `GOOGLE_DRIVE_CRED ∉ SYSTEM_CREDENTIALS`    |

Proof nested-ness is innocent: in flow 81 the STANDALONE `WebSearchTool` step
(var 456), whose stored `bubble_parameters` carried a user FIRECRAWL binding,
ran green — the nested `FirecrawlBubble` received the credential through the
pass-through at `web-search-tool.ts:130-141`. The failing steps were the
AI-agent's tool calls, whose agent bubble had `credentials: []` because nothing
is allowed to bind a SYSTEM-typed credential to it. A hypothetical agent tool
requiring a NON-system credential (e.g. a gmail tool) auto-binds fine: parser
`extractToolCredentials` puts it in `requiredCredentials`, server
`autoBindMissingCredentials` binds it, injector unions it. Nested-ness changes
nothing on any credential surface; the only tool-vs-service distinction anywhere
in the renderer is the cosmetic sub-bubble expander
(`FlowVisualizer.tsx` `hasSubBubbles` from `dependencyGraph`).

**The real differentiator is the credential's SYSTEM classification combined
with a platform that does not actually provide it.**

## 1. Root cause (file:line evidence)

`FIRECRAWL_API_KEY` is declared platform-provided:
`packages/bubble-shared-schemas/src/credential-schema.ts:884-886`
(`SYSTEM_CREDENTIALS` set). Two facts break the promise:

1. **The platform env is a trap.** Execution builds system credentials from
   `CREDENTIAL_ENV_MAP` (`apps/bubblelab-api/src/services/execution.ts:99-105`),
   and the map name for this type is `FIRE_CRAWL_API_KEY`
   (`credential-schema.ts:816`) — spelled differently from the credential type,
   so exporting `FIRECRAWL_API_KEY` is a silent no-op. The key sat empty on the
   live API until the interim workaround (now populated at
   `apps/bubblelab-api/.env:28`; BACKLOG "Done (historical)" marks that as
   superseded by S1).
2. **Every binding surface filters SYSTEM types, so no user credential can ever
   fill the gap and no heal restores a dropped binding:**
   - Setup tab: `apps/bubble-studio/src/components/FlowSetupPanel.tsx:192`
     `if (SYSTEM_CREDENTIALS.has(type)) continue;` — no card, user never told.
   - Node dropdown: `apps/bubble-studio/src/components/flow_visualizer/nodes/BubbleNode.tsx:224`
     (missing-badge suppressed) and `:300` + `:697-706` (slot renders "Use
     system default", never flagged missing, never auto-defaulted).
   - Studio auto-bind: `apps/bubble-studio/src/lib/credentialBinding.ts:155`
     (`computeAutoBindings`) and `:297` (`computeSuiteBindingProposals`) skip.
   - Run gate: `apps/bubble-studio/src/utils/flowValidation.ts:104` skips, so
     Execute never blocks on the unbound slot.
   - Server auto-bind/heal (the backstop that heals Google creds at
     create/GET/execution): `apps/bubblelab-api/src/services/credential-auto-bind.ts:224`
     `if (SYSTEM_CREDENTIALS.has(credentialType)) continue;`.
   - Chat cred widget special-case: `apps/bubble-studio/src/components/ai/ContextRequestWidget.tsx:47,59`.

Meanwhile detection reports the type (`bubble-flow-parser.ts:705-707` filter
commented out) and execution demands it (`FirecrawlBubble`'s own "FIRECRAWL_API_KEY
is required"). Result: a requirement everything announces and nothing can
satisfy. Runtime injection itself is sound — `CredentialHelper.getUserCredentials`
has no SYSTEM filter and `BubbleInjector` prefers user creds over system
(`BubbleInjector.ts:568-590`) — the credential is missing at run time only
because no surface was allowed to BIND it.

A masking side-effect discovered in the same forensics (out of S1 scope, see
open question 4): `web-scrape-tool.ts:165` throws "No content available in
markdown format" over the nested firecrawl failure, hiding the credential error.

## 3. Concrete fix plan

Principle: **one effective classification consulted by every layer.** A
credential type is _platform-provided_ only when the platform can actually
provide it (its `CREDENTIAL_ENV_MAP` env var is set). Declared-SYSTEM types
whose env is absent behave as user credentials end to end — Setup card, dropdown
auto-default, auto-bind/heal, run-blocking — identical to `GOOGLE_DRIVE_CRED`.

1. **`packages/bubble-shared-schemas/src/credential-schema.ts`** — add
   `getPlatformProvidedCredentials(env: Record<string,string|undefined>): Set<CredentialType>`
   = `SYSTEM_CREDENTIALS` ∩ types whose `CREDENTIAL_ENV_MAP` name is non-empty
   in `env`. `SYSTEM_CREDENTIALS` stays as declared intent (and as the studio's
   conservative fallback).
2. **API — `credential-auto-bind.ts:224`** — replace the `SYSTEM_CREDENTIALS`
   skip with the effective set (computed once per process from `process.env`).
   Non-backed SYSTEM types now auto-bind and heal from matching user creds at
   create/GET/generation/execution, same single-match backstop as Google creds.
3. **API — `GET /credentials` (`routes/credentials.ts`)** — add
   `platformCredentialTypes: CredentialType[]` to the response (the effective
   set). One seam, already fetched by every studio surface.
4. **Studio — one shared predicate** (new small helper, e.g.
   `lib/platformCredentials.ts`: `isPlatformProvided(type, platformTypes | undefined)`
   falling back to `SYSTEM_CREDENTIALS` while the query is unloaded). Swap the
   six filter sites to it: `FlowSetupPanel.tsx:192`, `BubbleNode.tsx:224,300`,
   `credentialBinding.ts:155,297` (thread the set through
   `ComputeAutoBindingsInput`), `flowValidation.ts:104`,
   `ContextRequestWidget.tsx:47,59`.
5. **API — `bubbleflow-generation-prompts.ts:181`** — advertise the effective
   set, so codegen stops telling the model Firecrawl is auto-managed on
   deployments where it is not.
6. **Env-name trap** — document `FIRE_CRAWL_API_KEY` at
   `credential-schema.ts:816` (or resolve per open question 3).

**Invariants to hold:**

- Env-backed SYSTEM creds (OPENAI, ANTHROPIC, etc. on the live stack) keep
  today's behavior at every surface: hidden from Setup, "Use system default"
  slot, never block Execute, injected from env.
- Detection stays complete (`bubble-flow-parser.ts` untouched; the commented
  filter stays out) — classification is applied at binding/presentation only.
- Injection precedence unchanged: user credential overrides system env
  (`BubbleInjector.ts:568-590`); wildcard skip logic unchanged.
- Clone/twin invariant unchanged: bindings canonicalize to
  `clonedFromVariableId ?? variableId`; `unionTwinCredentials` mirroring in
  `autoBindMissingCredentials` untouched.
- Studio pre-load fallback = current behavior (treat declared-SYSTEM as system)
  so no flash of "Missing" badges on env-backed creds.

**Dead code to remove after build:** none expected — `SYSTEM_CREDENTIALS`
remains referenced (definition of declared intent + fallback). Post-build check:
if any studio file's only reference was a swapped filter and its import went
unused, drop the import. `scope-audit-service.ts` / `account-email-defaults.ts`
keep the raw set (scope/OAuth logic, unaffected by API-key creds).

## 4. Event-based acceptance test (Pillar 2 — no DOM)

Thin script on `scripts/event-test/` (F0.1). Stack via `scripts/dev-stack.sh`
with `FIRE_CRAWL_API_KEY` **unset** for the API (proves the user-cred path).
Seed a user `FIRECRAWL_API_KEY` credential (value = the real key) plus a bound
Google Drive credential as the direct-bubble control.

Setup: `POST /bubble-flow` with code containing (i) an ai-agent whose `tools`
include `web-search-tool`, (ii) a direct `GoogleDriveBubble` step. No manual
credential selection anywhere.

Assertions (all exit-coded):

1. **(a) runtime assignment — API state:** `GET /bubble-flow/:id` →
   `requiredCredentials[<agentVarId>]` contains `"FIRECRAWL_API_KEY"`, and the
   agent entry in `bubbleParameters` carries a `credentials` parameter whose
   value maps `FIRECRAWL_API_KEY` → the seeded credential id — **same shape** as
   the Google Drive entry's `GOOGLE_DRIVE_CRED` binding (the equivalence IS the
   assertion: nested tool == direct bubble).
2. **(a) runtime assignment — run events:** `POST /bubble-flow/:id/execute-stream`
   SSE: `bubble_execution_complete` for the agent step has `result.success === true`;
   zero `error`/`fatal`/`warn` events whose message contains
   `"FIRECRAWL_API_KEY is required"`; `execution_complete.success === true`.
   Then `GET /bubble-flow/:id/executions?limit=1` → `items[0].result` persisted
   success. `collectRunErrorSignals(events)` returns `[]`.
3. **(b) dropdown auto-default — pure + persisted:** vitest on
   `computeAutoBindings`: input = agent bubble requiring `FIRECRAWL_API_KEY`,
   one connected FIRECRAWL credential, `platformCredentialTypes` excluding it →
   returns exactly one `AutoBinding` for that slot; same input with
   `platformCredentialTypes` including `OPENAI_CRED` proposes nothing for
   OPENAI. Integration: drive the flow page once with `agent-browser`
   (studio-test.mjs), then assert `GET /bubble-flow/:id` shows the binding
   persisted by `usePersistCredentialBindings` and `GET /telemetry` holds no
   `setup.*` error rows — data endpoints, never pixels.
4. **(c) Setup-tab detection — predicate + seam:** `GET /credentials` →
   `platformCredentialTypes` excludes `FIRECRAWL_API_KEY` (env unset); vitest on
   the shared predicate/entry-derivation: given flow 1's `requiredCredentials` +
   that set, the derived Setup entries include a `FIRECRAWL_API_KEY` card
   exactly as they include the `GOOGLE_DRIVE_CRED` card.
5. **Negative control (invariant):** restart API with `FIRE_CRAWL_API_KEY` set →
   `GET /credentials.platformCredentialTypes` includes `FIRECRAWL_API_KEY`; the
   create-time auto-bind leaves the agent slot unbound (skipped); a run still
   succeeds via env injection (`execute-stream` success events as in #2).

## 5. Risks + open questions

**Risks**

- Behavior change on deployments with missing env for OTHER declared-SYSTEM
  types (RESEND, APIFY, AI provider keys): those types will start surfacing in
  Setup and can block Execute via `flowValidation`. Previously they failed at
  runtime ("No OPENAI credentials provided"); surfacing earlier is correct but
  visible. The live stack has the AI keys set, so no expected change there.
- Studio depends on a server-computed set: the pre-load fallback must be the
  conservative current behavior or env-backed creds flash "Missing".
- `bubbleflow-generation-prompts` change shifts codegen phrasing; low risk, but
  regenerate-and-diff one flow before merge.
- Server processes cache the effective set at boot; changing `.env` needs an API
  restart (already true of `execution.ts` env reads).
- S1 `depends-on` F0.1: the event-test harness does not exist yet; the test
  script above assumes it.

**Open questions for the user (pre-execution)**

1. Confirm the systemic semantics: non-env-backed declared-SYSTEM creds behave
   as user creds at ALL surfaces (proposed), vs. the narrow one-off of removing
   `FIRECRAWL_API_KEY` from `SYSTEM_CREDENTIALS`. The systemic option also
   changes RESEND/APIFY/etc. on any deployment with holes in env.
2. When the env IS set AND a user credential is bound, the user credential wins
   at injection today (`BubbleInjector.ts:568`). Keep that precedence? (Proposed:
   yes, unchanged.)
3. `CREDENTIAL_ENV_MAP` name trap: keep `FIRE_CRAWL_API_KEY` (live `.env:28`
   already uses it) and document, or rename to `FIRECRAWL_API_KEY` and migrate
   `.env` in the same PR?
4. `web-scrape-tool.ts:165` masks the nested firecrawl failure ("No content
   available") — file as a fresh BACKLOG row (S5-adjacent error-signal fidelity)
   rather than folding into S1?
