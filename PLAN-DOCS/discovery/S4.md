# S4 discovery: requirement-completeness (self-test verifies fulfillment; dependency chains must not mask failures)

Backlog row: **S4** (Phase 1, depends-on F0.1). Status: discovery only, no source touched.
Accept (from BACKLOG.md:69): a flow where step 1 returns empty still exercises step 2; the run's `collectRunErrorSignals` surfaces every independent failure in one run (no masking).

---

## 1. Root cause (file:line evidence)

Three stacked layers. Each read from the code on `phase4-builder-harness`.

### Layer 1: the self-test's success gate is weaker than the product's own failure detector

`test_run_flow` (services/builder-agent/src/tools.ts:424-449) reduces a run via
`GluuClient.executeFlowStream` (services/builder-agent/src/gluu-client.ts:300-426), whose
`consumeEvent` collects **only** `error`/`fatal` typed events
(gluu-client.ts:318-334) and computes

```
success: streamCompleted && errors.length === 0        // gluu-client.ts:419
```

The studio's canonical detector, `collectRunErrorSignals`
(apps/bubble-studio/src/utils/executionErrorSignals.ts:53-125), treats three MORE classes as failure:

- `bubble_execution_complete` whose `additionalData.result.success === false` (executionErrorSignals.ts:80-90),
- a result whose `data.status >= 400` (executionErrorSignals.ts:91-105),
- `execution_complete` whose `additionalData.success === false` (executionErrorSignals.ts:109-121).

Its own header documents the trap (executionErrorSignals.ts:4-9): a failed Google Sheets
bubble emits `bubble_execution_complete{result.success:false}` plus a `warn`, **no**
`error`/`fatal`, and `execution_complete` still reports `success:true`
(the run-level `success` flag means only "handle() did not throw":
packages/bubble-core/src/logging/StreamingBubbleLogger.ts:245-279; bubbles surface API
failure as `success:false` without throwing, per services/builder-agent/BUBBLELAB_SDK_DISTILLED.md:172).

Consequence: a run with failed steps returns `test_run_flow -> success:true`, and the SOP
declares the build done on exactly that flag (services/builder-agent/src/prompts.ts:38:
"The build is DONE only when a run returns success: true"). The self-test proves "it ran",
never "each step succeeded", let alone "the prompt was fulfilled".

### Layer 2: fulfillment is unverifiable because step outputs are discarded

`executeFlowStream` returns errors plus a single `finalResult` string truncated at 4000 chars
(gluu-client.ts:335-339, 175-178). Per-step outputs
(`bubble_execution_complete.additionalData.result`, StreamingBubbleLogger.ts:151-160) and
nested-tool outputs (`tool_call_complete.toolOutput`, StreamingBubbleLogger.ts:477-491) are
dropped. The agent has no data to check the prompt's deliverables (doc has content, row
appended, message sent), and no SOP step requires a requirement-by-requirement check.

### Layer 3: dependency chains mask downstream and nested failures

- **Nested tools:** `web-scrape-tool` returns `{success:false, content:''}` on failure
  (packages/bubble-core/src/bubbles/tool-bubble/web-scrape-tool.ts:225-243, throw at :165).
  Used as an ai-agent tool, that failure lives only in `tool_call_complete.toolOutput`; the
  ai-agent step itself completes `success:true`. Neither the sidecar reducer nor
  `collectRunErrorSignals` has a `tool_call_complete` branch, so the failure is invisible
  everywhere (field case: flow 81, scrape fails, agent writes a doc around empty content, run all green).
- **Early-return chains:** the SDK rule "Always check `result.success` before touching
  `result.data`" (BUBBLELAB_SDK_DISTILLED.md:172) leads generated `handle()` code to
  early-return on the first failed step, so step 2 is never exercised and one run surfaces
  one failure at a time. FIXING_SKILL asserts "A flow keeps running after a failed step"
  (prompts.ts:159), but no authoring rule makes generated code continue past a failed
  independent step, so the premise does not hold for early-return code.

## 3. Concrete fix plan

### 3a. `services/builder-agent/src/gluu-client.ts`

- Port `collectRunErrorSignals` semantics into a mirrored pure function
  (`collectRunSignals(events)`), with a keep-in-sync header naming
  `apps/bubble-studio/src/utils/executionErrorSignals.ts` (same discipline as the marker literal).
- Add one sidecar-only extension: `tool_call_complete` whose `toolOutput.success === false`
  produces a signal `{source:'tool'}` (closes the nested-tool blind spot for the self-test).
- Extend `FlowRunSummary`:
  - `signals: RunSignal[]` (source `event | bubble | http | run | tool`, label, message, step name),
  - `stepOutcomes: [{variableId, variableName, bubbleName, success, outputDigest, emptyOutput}]`
    from every `bubble_execution_complete` (digest truncated ~600 chars),
  - `toolCalls: [{toolName, success, outputDigest, emptyOutput}]` from every `tool_call_complete`,
  - `success = streamCompleted && signals.length === 0`.
- `emptyOutput` heuristic: `success:true` with an empty primary payload (`''` content, `[]`
  values, nullish `data`). It is **data for the agent's judgment, never a hard failure** (a
  delete step legitimately returns nothing).
- Remove `FlowRunError` if `RunSignal` supersedes it and no importer remains (grep confirms it
  is internal to gluu-client + the pass-through in tools.ts today).

### 3b. `services/builder-agent/src/tools.ts` (test_run_flow, :424-449)

- Return the extended summary unchanged in shape discipline (still `textResult`).
- Rewrite the tool description: done requires `success:true` (signal-free) AND an explicit
  fulfillment check of the prompt's deliverables against `stepOutcomes` / `toolCalls` /
  `finalResult`; an `emptyOutput` on a content-producing step means NOT fulfilled.

### 3c. `services/builder-agent/src/prompts.ts`

- SOP step 8 split:
  - **8a run gate:** any signal (failed step, HTTP >= 400, run failure, failed nested tool)
    means the run failed even when no `error`/`fatal` event exists; fix and rerun.
  - **8b fulfillment gate:** enumerate the prompt's concrete deliverables, verify each one
    against `stepOutcomes` + `finalResult` (content non-empty where content was promised,
    resource link present, send step present). Done requires both gates.
- New authoring rule (beside the call-site rule, prompts.ts:49-59): on a failed or empty
  step, record the failure into the flow's returned result and CONTINUE with every step not
  data-dependent on it; never early-return the whole `handle()` on a single step failure.
  This makes FIXING_SKILL's premise (prompts.ts:159) true and lets one run carry every
  independent failure, which is what `collectRunErrorSignals` then surfaces.
- FIXING_SKILL step 2 Branch A (prompts.ts:164): "until it returns success: true" becomes
  "until the run is signal-free AND the deliverables check out".

### Invariants to hold

1. `test_run_flow` keeps executing via `POST /bubble-flow/:id/execute-stream`
   (apps/bubblelab-api/src/routes/bubble-flows.ts:502), the same path as the studio Test
   Flow button. No parallel executor.
2. Studio `collectRunErrorSignals` semantics unchanged; the sidecar is a strict superset
   (adds `tool` source + emptyOutput data). Explain-with-Gluu behavior untouched.
3. Success only gets stricter: any run the new reducer calls `success:true` was also
   `success:true` under the old reducer (no new false positives).
4. Timeout/abort behavior (gluu-client.ts:400-416) and `GluuApiError` propagation unchanged.
5. `report_missing_credential` exception (never run while a credential is missing) unchanged.

### Dead code to remove after

- `FlowRunError` interface (gluu-client.ts:155-162) once `RunSignal` replaces it.
- No importer becomes orphaned (surface above shows `executeFlowStream` has one caller).

## 4. Event-based acceptance test (Pillar 2, on the F0.1 harness)

Script: `scripts/event-test/s4-requirement-completeness.mjs`, exit-coded, structured JSON report. No DOM reads anywhere.

**Test A, deterministic (failed-step gate + no masking).** Create a fixture flow via
`POST /bubble-flow` with two independent http-bubble steps: step 1 GETs a guaranteed-404 URL
(the API's own base + `/definitely-missing`), step 2 GETs a known-200 URL; the code follows
the new continue-past-failure rule. Drive `POST /bubble-flow/:id/execute-stream`, capture
every SSE `StreamingLogEvent`. Assert:

1. Events contain `bubble_execution_complete` for BOTH step `variableName`s (step 2 exercised despite step 1 failing).
2. Running the captured events through the studio collector yields `>= 1` signal naming step 1 (`http`/`bubble` source), and running a variant fixture with two failing steps yields `>= 2` signals with distinct step names in ONE run (no masking).
3. Sidecar parity: run the same fixture through the sidecar reducer (import `gluu-client.ts` under node, call `executeFlowStream`) and assert `summary.success === false` and `summary.signals` maps 1:1 (source + step name) to the studio collector's list.
4. `GET /bubble-flow/:id/executions?limit=1` (bubble-flows.ts:1069-1095): `items[0].result` records both step outcomes (the continuation rule persisted both failures into the run history).

**Test B, unit-level parity + nested tool (deterministic).** A fixture JSON of captured events
(mirroring `executionErrorSignals.test.ts` cases, plus a flow-81-style
`tool_call_complete{toolOutput:{success:false, content:''}}` inside a green ai-agent step)
fed to the sidecar reducer. Assert: for the shared classes the two collectors emit identical
signal lists; for the nested-tool fixture the sidecar emits a `{source:'tool'}` signal and
`summary.success === false` while old-reducer semantics would have said `true`.

**Test C, agent-loop (transcript-asserted, nondeterministic, run last).** Drive a real build
via `POST /build/:flowId/message` with a prompt whose deliverable is checkable ("fetch URL X
and return its content as the result", X serving an empty body). Assert from
`GET /build/:flowId/thread -> transcript[].blocks[]`:

1. a `tool_use{name:'mcp__builder__test_run_flow'}` block exists (self-test ran);
2. after any `test_run_flow` whose returned summary carried signals or `emptyOutput` on the deliverable step, the transcript contains further `tool_use` blocks (`validate_flow`/`save_flow` then `test_run_flow` again) before the final assistant message (the agent iterated instead of declaring done);
3. the build thread status ends `ready` only when the last `test_run_flow` in the transcript was signal-free.

## 5. Risks

- **Mirror drift:** the sidecar's collector copy can drift from the studio's. Mitigated by Test B parity fixtures; the structural fix is Q1.
- **Stricter gate loops the agent longer** on flows with genuinely-expected non-2xx steps (e.g. probing for absence). Same semantics the studio's Explain affordance already applies; accepted.
- **emptyOutput false positives** (steps that legitimately return nothing). By design it is advisory data, not a gate; the SOP tells the agent to judge it against the prompt.
- **Test C nondeterminism** (real agent turns). It is the last, non-blocking tier; A and B are the deterministic gate.
- **Continue-past-failure changes generated code shape.** Applies only to newly authored or newly fixed flows; saved flows are untouched.
- `warn` events remain a non-signal in both collectors (matches studio today); if warn-only failures exist beyond the sheets case they stay invisible. Belongs to S5 if real.

## Open questions (user decision before execution)

1. **Shared collector vs mirror:** add `services/*` to `pnpm-workspace.yaml` so the sidecar imports one collector from `@bubblelab/shared-schemas` (build-order + stale-dist risk per memory), or keep the mirrored-function + parity-test pattern? Recommendation: mirror for S4, consolidate if the sidecar ever joins the workspace.
2. **Studio parity for nested-tool signals:** should `tool_call_complete{toolOutput.success:false}` also become a signal in the studio's `collectRunErrorSignals` so Explain-with-Gluu fires on nested-tool failures? That widens S4 toward S1/S5; sidecar-only for now unless you want both.
3. **Fulfillment mechanism strength:** SOP-driven agent judgment over `stepOutcomes` (recommended now) vs a structured `expectations` argument on `test_run_flow` (machine-checkable `{step, mustBeNonEmpty}` list; more testable, more rigid). Recommendation: SOP + emptyOutput data first; add `expectations` as a follow-up row if the agent under-verifies in practice.
4. **Continue-past-failure enforcement:** SOP-only (recommended, S4 scope) or also a lint rejecting top-level `return` inside `if (!x.success)` (S2-adjacent, new backlog row if wanted).
