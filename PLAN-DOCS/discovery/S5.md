# S5 discovery brief: collated run-error signals must carry the failing URL / variable name

Backlog row: **S5** (Phase 1, depends-on F0.1). Accept: a flow with two distinct
failing HTTP steps produces two signals whose messages differ (URL/var), and one
Explain-with-Gluu turn edits _both_ sites (thread shows two fixes).

Status: discovery only. No source file modified.

---

## 1. Root cause (file:line evidence)

Three layers each drop the identity; the collator sits at the end and cannot
recover what the layers below discarded, even though the event stream as a
whole still contains it.

### Layer 1: emit site erases the variable name

`packages/bubble-core/src/types/base-bubble-class.ts` passes `this.name` (the
bubble class name, e.g. `"http"`) as **both** the `bubbleName` and the
`variableName` argument on every completion log call:

- `action()` start log, line 260-264: `logger?.logBubbleExecution(this.context?.variableId ?? -999, this.name, this.name, sanitizeParams(...))`
- completion calls at lines 274-279, 305-310, 320-330, 359-364, 388-398, 427-432: all `logBubbleExecutionComplete(variableId, this.name, this.name, result)`

`packages/bubble-core/src/logging/StreamingBubbleLogger.ts:151-161` forwards
those arguments verbatim into the `bubble_execution_complete` event. Result:
`event.variableName === event.bubbleName === "http"` for every HttpBubble in
the flow. The only unique identity on the event is `event.variableId`
(and `additionalData.variableId`).

### Layer 2: the HTTP result omits the request URL

`packages/bubble-core/src/bubbles/service-bubble/http.ts`:

- `HttpResultSchema` (lines 86-116) has no `url` field.
- The result object (lines 331-345) and the catch-path result (lines 358-370)
  carry only status/statusText/body/etc.
- The failure string is `` `HTTP ${response.status}: ${response.statusText}` ``
  (line 342). Two different endpoints returning 404 produce byte-identical
  error strings.

The URL survives in exactly one place: the `bubble_execution` **start** event.
`StreamingBubbleLogger.logBubbleExecution` (lines 118-128) emits
`additionalData: { parameters, variableId }`, and `sanitizeParams`
(`packages/bubble-shared-schemas/src/param-utils.ts:10-17`) strips only keys
starting with `credentials`, so `parameters.url` is present on the wire.

### Layer 3: the collator collapses to the non-unique name and never joins

`apps/bubble-studio/src/utils/executionErrorSignals.ts`:

- Lines 76-79: `stepName = event.bubbleName || event.variableName || \`step ${event.variableId ?? '?'}\``.
`bubbleName`("http") wins;`variableId` never reaches the message.
- The `bubble` signal message (line 86) and `http` signal message (line 98)
  therefore read `Step "http" failed: HTTP 404: Not Found` for every failing
  HTTP step in the run.
- No join to the same run's `bubble_execution` start events, so the URL that
  the stream carries is discarded.
- `composeFixRequestMessage` (lines 133-161) numbers these identical lines and
  appends `JSON.stringify(additionalData).slice(0, 1500)` (line 145), which
  holds the response body, not the request URL, and truncates.

Net effect: the fix request Gluu receives lists N indistinguishable failures,
and `services/builder-agent/src/prompts.ts` FIXING_SKILL (line 159) tells the
agent those pasted signals ARE the run logs and are authoritative. The fixer
cannot tell two identical-looking failures apart, so it conflates them.

## 3. Concrete fix plan

Studio-side collation fix. bubble-core stays untouched (no wire-format change,
no shared-schemas/core/runtime rebuild chain, no blast radius into
WebhookStreamLogger or the API).

### 3a. `apps/bubble-studio/src/utils/executionErrorSignals.ts`

1. Extend `RunErrorSignal` with machine-readable identity:
   `variableId?: number; variableName?: string; url?: string; operation?: string`.
2. `collectRunErrorSignals(events, bubbleParameters?)`: add an optional second
   parameter (`Record<string | number, unknown>`, the flow's
   `bubbleParameters`). While iterating events, keep a per-`variableId` list of
   `bubble_execution` start events seen so far. On each failure signal:
   - resolve `variableName` via `findBubbleByVariableId(bubbleParameters, variableId)`
     (import from `../utils/bubbleUtils`);
   - join `url` / `operation` from the **nearest unconsumed preceding** start
     event with the same `variableId` (`additionalData.parameters.url` /
     `.operation`). Nearest-preceding, consume-on-match, so loop iterations of
     one call site each pair with their own start.
3. Message format (both `bubble` and `http` sources):
   `Step "<variableName ?? bubbleName>" (<bubbleName>#<variableId>, url: <url>) failed: <reason>`,
   with the `(...)` identity segment always present when `variableId` exists and
   the `url:` part present only when a URL was joined. Identity lives in the
   message line itself, ahead of the 1500-char additionalData slice, so
   truncation can never remove it.
4. `composeFixRequestMessage(events, issueDetails?, bubbleParameters?)`: thread
   the new parameter through; per-signal numbered lines inherit the identity.

### 3b. `apps/bubble-studio/src/components/execution_logs/AllEventsView.tsx`

Pass the already-available `bubbleParameters` (line 78) into the three call
sites (291 via `composeFixRequestMessage`, 757, 1370).

### 3c. `services/builder-agent/src/prompts.ts` (FIXING_SKILL, line ~159)

Update the report description: each numbered signal now names the step's
variable name, `bubbleName#variableId`, and the failing URL when the step made
an HTTP request. Add one procedure sentence: treat each distinct
`variableId`/URL as its own fix site; two signals with the same bubble name are
different call sites unless their variableIds match. `FIX_REQUEST_MARKER`
literal stays byte-identical in both files (documented sync at
`executionErrorSignals.ts:14-17` and `prompts.ts:143-148`).

### 3d. `apps/bubble-studio/src/utils/executionErrorSignals.test.ts`

Extend fixtures: two failing HTTP pairs (start + complete) with distinct
variableIds and URLs; assertions in section 4.

### Invariants to hold

- Two distinct failing call sites always produce signals whose `message`
  strings differ, and each signal carries `variableId`.
- `bubbleParameters` stays optional: the collector still works event-only
  (identity falls back to `bubbleName#variableId` + joined URL), so no caller
  is forced to change.
- Event wire format unchanged; no bubble-core/runtime rebuild.
- Marker literals stay in sync across studio and sidecar.
- Existing single-failure behavior (flow-64 google-sheets shape) keeps working;
  its message gains the identity suffix only.

### Dead code to remove after

None expected: both changed functions gain optional parameters, so no importer
is orphaned. Post-build check: confirm `BubbleResultShape` gained no unused
fields and no test fixture became unreferenced.

## 4. Event-based acceptance test (Pillar 2, no DOM)

### Test A: unit (vitest, runs today, no F0.1 needed)

`cd apps/bubble-studio && pnpm vitest run src/utils/executionErrorSignals.test.ts`

Fixture: events list containing, in order,
`bubble_execution{variableId:111, additionalData.parameters.url:'https://api.a.example/x'}`,
`bubble_execution_complete{variableId:111, result:{success:true, data:{status:404, statusText:'Not Found'}}}`,
`bubble_execution{variableId:222, additionalData.parameters.url:'https://api.b.example/y'}`,
`bubble_execution_complete{variableId:222, result:{success:false, error:'HTTP 404: Not Found', data:{status:404}}}`,
plus `bubbleParameters = {111:{variableId:111, variableName:'fetchAlpha', bubbleName:'http'}, 222:{variableId:222, variableName:'fetchBeta', bubbleName:'http'}}`.

Assertions:

1. `signals.length === 2`.
2. `signals[0].message !== signals[1].message`.
3. `signals[0].message` contains `'https://api.a.example/x'` and `'fetchAlpha'`;
   `signals[1].message` contains `'https://api.b.example/y'` and `'fetchBeta'`.
4. `signals[0].variableId === 111`, `signals[1].variableId === 222`,
   `signals[0].url` / `signals[1].url` equal the two URLs.
5. Without `bubbleParameters`: messages still differ and contain
   `'http#111'` / `'http#222'` plus the joined URLs.
6. `composeFixRequestMessage(events, undefined, bubbleParameters)` contains
   `'2 error signals'`, both URLs, and two numbered lines that differ.
7. Loop shape: two start/complete pairs sharing `variableId:111` with different
   URLs yield two signals carrying their own URLs (nearest-preceding join).

## 5. Risks and open questions

Risks:

1. **`variableId ?? -999` fallback** (`base-bubble-class.ts:261`): bubbles run
   without an injected context (nested/agent-built tools) all share `-999`, so
   identity degrades to the joined URL alone, and same-URL failures still
   conflate. That is S1's nested-tool recognition territory; S5 does not fix
   the emit layer. The nearest-preceding-start join keeps sequential `-999`
   pairs correct; concurrent `Promise.all` calls sharing one variableId can
   still misjoin (accepted, rare).
2. **F0.5 non-technical principle vs identity strings**: the Errors panel
   renders `signal.message` verbatim (`AllEventsView.tsx:964-991`), so
   `(http#287300, url: ...)` leaks technical detail into the UI. Default in
   this plan: ship the full identity in both places, since the same message
   feeds the fixer; revisit at U-phase if the panel needs a friendlier split
   (e.g. render `variableName` + URL, keep `#variableId` only in the composed
   fix message).
3. **Sidecar prompt drift**: FIXING_SKILL prose must match the new line format;
   both files carry sync comments, and the marker literal is unchanged, so
   `isFixRequest` keeps matching.
4. **External regression script** `/home/unix/vercel-browser-agent/gluu-fix-test.mjs`
   may assert old message text; re-run and update it after the change.
5. **httpbin.org flake** in Test B: external dependency; a local stub server in
   the harness removes it.

Open questions for the user (defaults stated, execution can proceed on them):

1. Accept the full identity string in the visible Errors panel (risk 2), or
   split UI-friendly vs fixer-verbose now?
2. Emit-layer fix (thread the real `variableName` from the dependency graph
   node at `base-bubble-class.ts:161-173` into the logger calls) — fold into
   S5 or leave for S1? Default: leave for S1.
3. Test B target: httpbin vs local stub? Default: local stub via the F0.1
   harness.
