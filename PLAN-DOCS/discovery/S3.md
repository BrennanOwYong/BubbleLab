# S3 — Tool-suite-family intelligence: capability → owning-bubble discovery

Discovery/design brief. Status: design only, no source modified. Backlog row:
S3 (Phase 1, depends-on F0.1). Governed by `DISPATCH-CONTRACT.md` (Pillar 5
dependency surface recorded below; Pillar 2 event-based acceptance at the end).

## Problem

Capabilities that live INSIDE an owning bubble under a different product name
are not discoverable by what they do. The canonical case: "put it in a Google
Doc" must resolve to `GoogleDriveBubble` (`upload_file` with
`convert_to_google_docs: true`, or `update_doc`/`copy_doc`/`replace_text`),
but no bubble is named "google-docs", so the builder agent can miss the
requirement entirely (flow 80, memory `call-site-silent-failure-and-tool-suite-kivs`).
Backlog acceptance: build-from-prompt "put it in a Google Doc" yields a flow
whose run emits a `google-drive` `success:true` step producing a doc link in
`finalResult`.

## Root cause (file:line evidence)

Capability→bubble resolution is exact-registry-name-only at every surface the
live build path touches. Four links in the chain:

1. **The sole live build path is the sidecar builder agent**, and its entire
   capability catalog is a static 9-bubble excerpt. The flow-builder toolset is
   `get_bubble_details, validate_flow, save_flow, get_flow,
provision_spreadsheet, seed_rows, set_flow_defaults, test_run_flow,
rename_flow` (`services/builder-agent/src/tools.ts:216-453`); no tool
   enumerates or searches the registry. The agent's only catalog is
   `services/builder-agent/BUBBLELAB_SDK_DISTILLED.md` §4 "Bubble reference
   (demo-relevant set)" (lines 213-334, 9 bubbles), loaded verbatim into the
   system prompt (`services/builder-agent/src/prompts.ts:20-23,179`). The
   registry holds 60+ bubbles
   (`packages/bubble-core/src/bubble-factory.ts:511-580`, 60 single-line
   `register(...)` calls plus multi-line ones); the other ~50 (slack, github,
   discord, airtable, stripe, ...) are invisible to the agent.
   The legacy `/generate` path is dead: `bubbleflow-generation-prompts.ts` has
   no live importer (`grep` finds only itself plus a comment in
   `packages/bubble-core/src/utils/codegen-narrow.ts`), and `routes/ai.ts` is
   speech-to-text only.

2. **`get_bubble_details` resolves by exact registry key, and a miss is a dead
   end.** `GetBubbleDetailsTool.performAction` calls
   `factory.getMetadata(name)` which is `this.get(name)`, a `Map` lookup on
   the registered name (`packages/bubble-core/src/bubble-factory.ts:738-740`).
   A miss throws `Bubble '<name>' not found in registry`
   (`packages/bubble-core/src/bubbles/tool-bubble/get-bubble-details-tool.ts:115-119`);
   the API wraps that as a bare 404
   (`apps/bubblelab-api/src/routes/bubble-flows.ts:592-621`); the sidecar tool
   surfaces it as an error string truncated to 300 chars
   (`services/builder-agent/src/tools.ts:80-84`). Live probe against the
   running API (2026-08-01):
   `GET /bubble-flow/bubble-details/google-docs` →
   `{"error":"Bubble 'google-docs' not found in registry"}` and even the
   DECLARED alias `gdrive` (`google-drive.ts:961`) returns the same 404. Alias
   is write-only metadata; nothing resolves by it. No suggestion, no owning
   bubble, no redirect.

3. **The capability knowledge already exists in registry metadata but nothing
   indexes it.** `GoogleDriveBubble.shortDescription` says "Google Drive
   integration with full Google Docs tab support..." and `longDescription` has
   a "Google Docs Tab Support" section
   (`packages/bubble-core/src/bubbles/service-bubble/google-drive.ts:931-960`).
   The distilled doc's §4.3 table lists every doc operation including
   `upload_file` `convert_to_google_docs=false` (doc lines 255-274). The
   knowledge is present; the lookup from a capability phrase ("Google Doc") to
   the owning bubble + operation does not exist. The SOP presumes the mapping
   is already known: "For EVERY bubble you will use, call get_bubble_details
   FIRST" (`services/builder-agent/src/prompts.ts:32`) — the agent must pick
   the bubble BEFORE the tool can help it.

4. **The registry-wide discovery bubble exists but is unwired and lossy.**
   `ListBubblesTool` (`packages/bubble-core/src/bubbles/tool-bubble/list-bubbles-tool.ts`)
   is registered but not exposed to the sidecar. Its `useCase` field comes from
   `extractUseCaseFromDescription`, a regex that requires a literal
   `Use cases:` heading (`list-bubbles-tool.ts:94-108`); `google-drive`'s
   `longDescription` has no such heading, so its listing collapses to the
   fallback "General purpose bubble for various workflow needs", dropping the
   Docs capability text even from this tool's output.

Systemic statement: every discovery surface keys on the bubble's registered
name. A capability whose product name differs from its owner's name (Docs in
Drive, Calendar events in a future google-calendar, database rows in Notion's
`query_data_source`) has no path from "what the user asked for" to "which
bubble + operation does it".

## Fix plan

Design principle: ground discovery in the registry metadata that already
exists (one source of truth), never a second hand-maintained mapping that can
drift. Four changes, smallest first:

1. **`GetBubbleDetailsTool`: a miss returns owning-bubble suggestions instead
   of a dead end.**
   (`packages/bubble-core/src/bubbles/tool-bubble/get-bubble-details-tool.ts:106-119`)
   - Resolve declared aliases before failing (scan `getAllMetadata()` for
     `alias === name`).
   - On a true miss, tokenize the query and score every registered bubble's
     `name + alias + shortDescription + longDescription` plus its operation
     literals (walk the params discriminated union the same way
     `generateOperationExamples` already does, :460-478). Return
     `success: false` with a new optional `suggestions:
{name, shortDescription, matchedOperations?}[]` field (cap 3) and an
     error string of the form
     `Bubble 'google-docs' not found. The capability may live inside:
google-drive (Google Docs support; operations get_doc, update_doc,
copy_doc, replace_text, upload_file{convert_to_google_docs}).`
   - Schema: add optional `suggestions` to `GetBubbleDetailsToolResultSchema`
     (:42-67). The sidecar's response parser is `.passthrough()`
     (`services/builder-agent/src/tools.ts:47-59`), so it tolerates the field.

2. **API endpoint forwards suggestions.**
   (`apps/bubblelab-api/src/routes/bubble-flows.ts:596-621`) On
   `!result.success`, put `suggestions` and the enriched error in the 404
   body. Sidecar: raise the error-text slice from 300 to ~600 chars
   (`services/builder-agent/src/tools.ts:82`) so the suggestion text survives.

3. **New `search_bubbles` tool on both sidecar servers, backed by a new API
   endpoint.**
   - API: `GET /bubble-flow/bubble-search?q=...` in `bubble-flows.ts`, ranking
     `factory.getAllMetadata()` by the same scorer as (1) and returning
     `{items: [{name, type, shortDescription, matchedOperations}]}`. Reuses the
     factory; registers no new bubble, so `BubbleName`/credential-schema/
     available-tools stay untouched.
   - Sidecar: `search_bubbles(query)` in `tools.ts` beside
     `makeGetBubbleDetailsTool` (:62-93), added to `createBuilderServer`
     (:212) and `createPageServer` (:509). Covered by the `mcp__builder__*`
     wildcard.

4. **Prompt-side: capability index + SOP rule.**
   - `BUBBLELAB_SDK_DISTILLED.md`: add a short "§4.0 Capability index" table
     ahead of the per-bubble tables: Google Doc (create) → `google-drive`
     `upload_file{convert_to_google_docs:true}`; Google Doc (read/write/
     template) → `get_doc`/`update_doc`/`copy_doc`/`replace_text`; Notion
     database query → `notion` `query_data_source`; email → `gmail`; any
     product name with no same-named bubble → `search_bubbles`.
   - `prompts.ts` BUILD_SOP step 2 (:32): append: when the user names a
     product or capability with no same-named bubble, call `search_bubbles`
     (or `get_bubble_details` with the product name; a miss now names the
     owning bubble) BEFORE concluding it is unsupported; never map a
     capability to a bubble from memory.

**Invariants to hold**

- `get_bubble_details` exact-name success path byte-identical (found-path code
  untouched; only the miss path changes).
- No new registered bubble: `BubbleName` union (`types.ts:173` region),
  `credential-schema.ts`, `available-tools.ts` unchanged.
- Prompt composition order preserved (`prompts.ts:177-181`: SOP + fix skill +
  SDK reference).
- Discovery only: the four-anchor call-site rules, credential injection, and
  validate/save semantics are untouched (S1/S2 own those).
- Sidecar restart after doc/prompt edits (readFileSync at module load).

**Dead code to remove after**: none created by this change. Recorded
observation (do NOT act in S3): `apps/bubblelab-api/src/config/
bubbleflow-generation-prompts.ts` has no live importer; it is the Pearl-era
generation rulebook the distilled doc cites as a source. Leave it; flag for a

## Event-based acceptance test (Pillar 2)

Thin script on `scripts/event-test/` (F0.1). Precondition: a stack via
`scripts/dev-stack.sh up` with a live `GOOGLE_DRIVE_CRED` connected. All
assertions read logged events/HTTP bodies, never the DOM. Exit non-zero on any
failure.

**Stage 1 — discovery mechanics (deterministic, no LLM):**

1. `GET /bubble-flow/bubble-details/google-docs` → assert status 404 AND
   `body.suggestions[0].name === 'google-drive'` AND
   `/google-drive/.test(body.error)`.
2. `GET /bubble-flow/bubble-details/gdrive` → assert status 200 AND
   `body.name === 'google-drive'` (alias resolution).
3. `GET /bubble-flow/bubble-search?q=google%20doc` → assert
   `body.items[0].name === 'google-drive'` AND
   `body.items[0].matchedOperations` includes `'update_doc'` or
   `'upload_file'`.

**Stage 2 — build-from-prompt (the S3 backlog acceptance):** 4. `POST /bubble-flow/empty` → `flowId`; send the build prompt
"Each morning summarize the text I give you and put it in a Google Doc,
then give me the link" through `POST /build/:flowId/message` (or the /build
SSE), wait for the done frame. 5. `GET /build/:flowId/thread` → assert the transcript contains a
`tool_use{name:'mcp__builder__save_flow'}` whose `input.code` matches
`/GoogleDriveBubble/` AND
`/convert_to_google_docs|update_doc|copy_doc/`; assert thread status is
`ready` (not `error`, not `blocked_on_credential` given the connected
cred); assert NO assistant block matches
/not (possible|supported|available)/i regarding Docs. 6. Discovery-path proof on an off-catalog capability (mechanism, not just the
Docs instance): a second build "when I say so, post 'hi' to my Discord
server" → assert the thread transcript contains a
`tool_use{name:'mcp__builder__search_bubbles'}` (discord is absent from
the distilled doc, so the agent cannot know it except via search), and its
result block names `discord`. 7. `GET /build/:flowId/thread` for the Docs flow → assert a
`tool_use{name:'mcp__builder__get_bubble_details', input.bubbleName:'google-drive'}`
block exists (SOP step 2 held).

**Stage 3 — run events (the backlog's literal accept):** 8. `POST /bubble-flow/:id/execute-stream` → collect SSE `StreamingLogEvent`s.
Assert one `bubble_execution_complete` with bubble name `google-drive` and
`result.success === true`; assert `execution_complete.success === true`;
assert `JSON.stringify(execution_complete.finalResult)` matches
`/docs\.google\.com|drive\.google\.com/` (the doc link). 9. `GET /bubble-flow/:id/executions?limit=1` → `items[0].result` carries the
same link (persisted). 10. `GET /telemetry` → no new studio client errors between test start/end.

## Risks

- **LLM nondeterminism (stage 2).** The distilled doc already lists the doc
  operations, so the agent may author correctly WITHOUT calling any discovery
  tool; assertion 7 could flake. Mitigation is built into the test design:
  assertion 5 is outcome-based (saved code + ops), and the mechanism proof
  rides assertion 6, where the capability is provably absent from the prompt
  catalog. If 7 flakes, drop it and keep 5+6 as the gate.
- **Suggestion ranking on generic tokens.** `q=google doc` shares a token
  with sheets/gmail/calendar; single-token scoring could rank the wrong owner
  first. Require multi-token AND-boosting and operation-literal matches to
  outrank description-only matches; cap at 3 suggestions.
- **Search exposes the full 60-bubble registry.** The agent could now select
  bubbles (stripe, snowflake, ...) whose credentials the studio UI cannot
  connect, producing flows the user cannot set up. See open question 2.
- **Hand-authored capability index drifts.** The §4.0 table is a static doc;
  new operations will not appear in it. The durable half is the
  registry-backed search; the table only covers the demo set. See open
  question 1.
- **404-body transport truncation.** The sidecar slices error text at 300
  chars (`tools.ts:82`); the plan raises it, but any future consumer of the
  bare `/bubble-details` 404 must read `suggestions` from the body, not parse
  the error string.

## Open questions (need the user before execution)

1. Capability index in the distilled doc: hand-author the small §4.0 table
   (fast, drifts) or generate it from registry metadata via a script
   (precedent: `packages/bubble-core/scripts/bubble-metadata-bundler.ts`)?
2. Should `search_bubbles` expose ALL registered bubbles, or filter to the
   set whose credentials the studio can actually connect (the demo set plus
   system-cred tools)? Exposing all risks flows the user cannot credential;
   filtering hides real capabilities.
3. Suggestion transport for a `get_bubble_details` miss: keep HTTP 404 with
   `suggestions` in the body, or switch to 200 `{success:false, suggestions}`?
   404 preserves the current endpoint contract; 200 simplifies the sidecar
   parse path.
4. Is assertion 7 (discovery tool call on the Docs prompt) required, or is
   outcome-only (5) plus the off-catalog mechanism proof (6) the gate?
