# U2 — Result node with headline-output button (discovery brief)

Status: DESIGN ONLY. No source touched. Governed by `DISPATCH-CONTRACT.md`;
backlog row: `BACKLOG.md` Phase 2, U2 (depends-on F0.1, S4).

## Problem

A run's most important value (the doc link, the summary, the number) is buried
in execution logs a non-technical user never opens. The builder agent already
knows what the flow is for; nothing captures "the one output that matters" or
surfaces it after a run. F0.5 (non-technical customer) makes raw
`finalResult` JSON unacceptable as the answer.

## Approach

Three additive seams, no refactor:

1. **Capture at build time (sidecar).** The flow-builder SOP gains one
   clarifying step: during intent determination the agent asks the user ONE
   question, "what single result do you most want to see after each run?"
   (plain language, per the existing "ask ONE direct question" rule in
   `services/builder-agent/src/prompts.ts:31`). After the self-test succeeds
   (SOP step 8), the agent calls a new `set_primary_output` tool with the
   top-level key of the `handle()` return object that answers it, plus a
   user-facing label. Invariant the SOP enforces: `handle()` returns an object
   and the registered key is a top-level property of it, so
   `finalResult[key]` is always defined on a successful run.
2. **Persist on the flow (API).** `bubble_flows.metadata` (jsonb, already
   returned by `GET /bubble-flow/:id` as `metadata`, route at
   `apps/bubblelab-api/src/routes/bubble-flows.ts:727` response line
   `metadata: flow.metadata || {}`) gains
   `primaryOutput: { key: string, label: string }`. A new
   `PATCH /bubble-flow/:id/primary-output` writes it (merge, ownership-checked),
   mirroring the rename route (`schemas/bubble-flows.ts:401`,
   `routes/bubble-flows.ts:816`). No migration: jsonb column exists in both
   `schema-postgres.ts:33` and `schema-sqlite.ts`, and the shared-schemas
   details response already types `metadata` as `record(string, unknown)`
   (`packages/bubble-shared-schemas/src/bubbleflow-schema.ts:390`).
3. **Surface after a run (studio).** A new `ResultNode` renders as the
   terminal node of the flow graph when `metadata.primaryOutput` exists. It
   shows one button carrying the label. On click it reveals the value of
   `finalResult[key]` from the latest run and emits a telemetry event (the
   Pillar-2 "new behavior must emit an event" rule). Value formatting per
   F0.5: URL -> an "Open" action, string/number -> a readable card, object ->
   flattened label:value lines. Never raw JSON.

### Where the value comes from (read path)

- Live run: `execution_complete` events carry
  `additionalData: { success, finalResult, error, summary }`
  (`packages/bubble-core/src/logging/StreamingBubbleLogger.ts:267`; same in
  `WebhookStreamLogger.ts:221`). The studio's `executionStore` keeps the full
  `events: StreamingLogEvent[]` array and replays history through
  `restoreFromHistory`, so one pure selector over events serves both live and
  restored runs. Today the store's `execution_complete` case
  (`apps/bubble-studio/src/stores/executionStore.ts:887`) drops
  `finalResult`; the selector reads it from the retained event, no store
  schema change required.
- Fresh page, no run selected: fall back to the newest item of
  `GET /bubble-flow/:id/executions?limit=1` -> `items[].result`
  (`routes/bubble-flows.ts:1033`), which persists the same final result.

The derivation lives in one exported pure function,
`deriveResultNodeValue(primaryOutput, events, latestExecutionResult)`, used by
the node and asserted by the acceptance test, so the test and the UI can never
diverge.

## Data model / state

```
bubble_flows.metadata.primaryOutput = {
  key:   string   // top-level property of the handle() return object
  label: string   // user-facing button text, agent-authored, plain language
}
```

- Absent -> no ResultNode rendered (all pre-U2 flows degrade gracefully).
- Typed accessor in the studio (a small `getPrimaryOutput(metadata)` narrow
  function) instead of casting the `record(string, unknown)` metadata.
- Studio state: no new store field. The node subscribes to
  `useExecutionStore((s) => s.events)` and `useExecutionHistory` fallback via
  the pure selector. (Option B, capturing `lastRunResult` in the store's
  `execution_complete` case, is a one-line upgrade if event-array clearing
  proves racy; not needed first.)

## User-facing clarifying question

One question shapes the SOP wording, ask the user before dispatch:

> When the prompt already makes the headline output obvious (e.g. "email me a
> daily digest" -> the digest doc link), should the agent still ask the
> question, or infer the output and state its choice in one sentence ("I'll
> surface the doc link after each run; tell me if you want something else")?
> Default if unanswered: infer-when-obvious, ask-when-ambiguous, so creation
> stays low-friction.

Secondary (defaultable): clicking the button when the value is a URL, reveal
the link with an Open action (default) vs. open a new tab outright.

## Event-based acceptance test (Pillar 2)

`scripts/event-test/u2-result-node.mjs`, on the F0.1 harness, exits non-zero
on any failed assertion. No DOM reads.

1. **Capture**: drive a real build (`POST /build/:flowId/message` with a
   prompt whose output is ambiguous). Assert from
   `GET /build/:flowId/thread` -> `transcript[].blocks[]`:
   a `tool_use{name:'set_primary_output'}` block exists and its
   `input.key`/`input.label` are non-empty. (Ask-vs-infer wording is a taste
   check, left to the USER-TEST card; the tool call is the hard gate.)
2. **Persist**: `GET /bubble-flow/:id` -> `metadata.primaryOutput.key`
   equals the tool call's `input.key`.
3. **Run**: `POST /bubble-flow/:id/execute-stream`; collect SSE. Assert
   `execution_complete.additionalData.success === true` and
   `additionalData.finalResult[key] !== undefined`.
4. **Surface**: assert
   `deriveResultNodeValue(primaryOutput, events, null)` (imported from the
   studio module) deep-equals `finalResult[key]`, proving the node surfaces
   exactly the run's value.
5. **Reveal event**: via `agent-browser`, click the ResultNode button; assert
   `GET /telemetry` contains `result_node_reveal` with the flow id and
   `hasValue: true`. Reads the telemetry log, not pixels.
6. **Negative**: a flow without `metadata.primaryOutput` produces no
   `result-node` in the derived node model (assert on the exported
   node-building output or on absence of the telemetry event after a full
   graph render), and `deriveResultNodeValue` returns null without throwing.

`[USER-TEST]` card ships with the PR (Pillar 1): setup = dev-stack up + one
seeded flow with a primary output + one completed run; judging = does the
question during creation feel helpful or naggy, is the button label the
user's own vocabulary, does the revealed value feel like "the answer" rather
than data.

  `metadata` response field already exists in
  `bubble-shared-schemas/bubbleflow-schema.ts:390`, so no shared-schemas

  refetch, no new frontend plumbing.

## Risks

1. **Fix-mode key drift.** The fixer rewrites `handle()` and renames or drops
   the registered key; the node then reveals `undefined`. Mitigated by the
   FIXING_SKILL rule (file 5) plus a warning in `test_run_flow`'s result when
   `metadata.primaryOutput.key` is absent from a successful run's
   `finalResult` (one added check in the tool, `tools.ts:424`), which the
   agent's own loop then corrects. Assertion 3 catches regressions.
2. **Non-object finalResult.** A flow returning a bare string breaks
   `finalResult[key]`. The SOP invariant (return an object) prevents it for
   new builds; `deriveResultNodeValue` returns null defensively for old ones.
3. **Layout-branch miss.** The visualizer has two layout branches
   (`shouldUseSequentialLayout`, FlowVisualizer ~:1114); placing the node in
   only one makes it disappear for fallback-layout flows. Assertion 6 plus
   placing the append after both branches converge guards this.
4. **Question fatigue.** Always-asking adds a turn to every build. The
   clarifying question above resolves it; the infer-when-obvious default
   keeps tempo.
5. **S4 ordering.** U2 depends on S4: until the self-test verifies the prompt
   was fulfilled (not merely ran), a "successful" run can carry a hollow
   `finalResult` and the node would proudly reveal an empty value. If U2 must
   land before S4, assertion 3 gives partial cover (key present and defined),
   but fulfillment-quality of the value stays S4's job.
6. **F0.1 not built.** The acceptance script presumes `scripts/event-test/`;
   it is TODO. Building U2's test standalone would fork the harness pattern,
   against F0.1's purpose.
