# S6 — Fixer binary-triage robustness: root-cause brief (discovery only)

Backlog row: S6 (Phase 1, depends-on F0.1, S1). Contract acceptance: inject a
bound-but-resolution-failing credential; the fixer's thread message does NOT
tell the user to reconnect; it diagnoses the resolution layer.

---

## 1. Root cause (file:line evidence)

The fixer classifies credential-shaped errors from error-message TEXT alone and
a hard-coded rule, with zero access to the actual credential state.

**(a) The prompt hard-codes "reconnect" for every auth-looking error.**
`services/builder-agent/src/prompts.ts:165` (FIXING_SKILL, Branch B):

> "For a credential or connection failure (missing key, "authentication
> failed", an expired or revoked OAuth connection, a token that no longer
> refreshes), the action is **ALWAYS**: tell the user to go to the Setup tab
> … and reconnect the exact named credential"

The same unconditional rule sits in the build SOP at `prompts.ts:80`. Both were
introduced by commit `28c4c37` (2026-07-31, "Branch B names the Setup tab
reconnect"). "ALWAYS" is the bug: it maps four distinct failure layers onto one
user action.

**(b) The flow agent has no tool that can see credential state.** The fix-mode
turn's procedure (`prompts.ts:162`) says "call get_flow … before judging any
cause", but:

- `get_flow` (`services/builder-agent/src/tools.ts:290-320`) surfaces only
  `requiredCredentials` (type names per bubble). The API's flow-detail response
  DOES include `bubbleParameters` with per-bubble bound credential ids
  (`apps/bubblelab-api/src/routes/bubble-flows.ts:726`; binding lives in the
  bubble's `credentials` parameter value `{CRED_TYPE: credId}`, written by
  `apps/bubblelab-api/src/services/credential-auto-bind.ts:85-108`), but the
  sidecar drops it: `flowDetailSchema`
  (`services/builder-agent/src/gluu-client.ts:45-67`) never declares it and the
  tool never returns it.
- `listCredentials` exists on the client (`gluu-client.ts:255`) but is exposed
  only to the PAGE agent as `list_integrations` (`tools.ts:537`). The flow
  agent — the one that runs fix mode — cannot list the user's credentials at
  all, and the client's `credentialSchema` (`gluu-client.ts:75-86`) omits
  `oauthStatus`/`oauthExpiresAt`, which the API already computes
  (`apps/bubblelab-api/src/routes/credentials.ts:151-165,179`).

**(c) The failure layers "reconnect" cannot help with are real and recurrent:**

1. **SYSTEM credentials** (`packages/bubble-shared-schemas/src/credential-schema.ts:884`
   — FIRECRAWL_API_KEY, OPENAI_CRED, …): platform-env creds
   (`apps/bubblelab-api/src/services/execution.ts:99-104` resolves them from
   `process.env`, never from user rows). The user has nothing to reconnect and
   the Setup tab does not even list SYSTEM types. Precedent: the Firecrawl
   misdiagnosis — the fixer declared the cred "required"/user-actionable while
   the actual failure was the platform env being empty (memory
   `call-site-silent-failure-and-tool-suite-kivs`).
2. **Bound but not injected at runtime** (resolution layer): a bubble at an
   unrecognized call site, or an S1 nested tool, runs credential-less and fails
   with an auth-shaped error while its slot IS bound (`prompts.ts:51` documents
   the trap; injection happens only for recognized call sites). A dangling
   `credentialId` (bound id whose row was deleted) fails the same way:
   `execution.ts`'s `userCredentialMapping` finds no secret, the bubble runs
   bare.
3. **Refresh-dead grant**: `apps/bubblelab-api/src/services/oauth-service.ts:489-496`
   falls back to the stored (expired) token on refresh failure and persists
   nothing, so the run shows "Authentication failed". Here reconnect IS the
   right action — but today the fixer cannot distinguish this layer from
   layers 1-2, so it cannot be trusted on any of them.

**Root cause in one line:** `prompts.ts:80,165` prescribe "reconnect" for any
auth-shaped error text, and the flow agent lacks any tool exposing bound-slot
state, credential health, or SYSTEM-ness — so classification cannot be grounded
in the failure layer.

## 3. Concrete fix plan

**(i) API — one additive endpoint** `GET /bubble-flow/:id/credential-state`
(`apps/bubblelab-api/src/routes/bubble-flows.ts`). For every non-clone
required-credential slot (skip via `isInvocationClone`), return:

```
{ slots: [{ bubbleKey, variableName, bubbleName, credentialType,
            system: boolean,                  // isSystemCredential()
            systemEnvPresent?: boolean,       // CREDENTIAL_ENV_MAP + process.env, as execution.ts:99-104
            boundCredentialId: number|null,   // from the bubble's credentials param
            boundCredential?: { id, name, oauthProvider, oauthStatus, oauthExpiresAt, createdAt },
            boundRowExists: boolean,          // dangling-id detection
            userCredentialsOfType: number     // count of connectable rows
}]}
```

Reuses `extractRequiredCredentials` + the `oauthStatus` computation already in
`routes/credentials.ts:151-165`. Single source of truth for SYSTEM/clone
predicates stays server-side.

**(ii) gluu-client.ts** — add `credentialStateSchema` +
`getFlowCredentialState(flowId)` (thin wrapper, consistent with the file's
"every method wraps one existing endpoint" contract). Add optional
`oauthStatus`/`oauthExpiresAt` to `credentialSchema` while there (the route
already returns them; the page agent's `list_integrations` gets them free).

**(iii) tools.ts** — new FLOW-agent tool `inspect_flow_credentials` wrapping
(ii), registered in `createBuilderServer` (`tools.ts:204`). Description states
the four layers and that it is MANDATORY before any credential-related Branch-B
instruction.

**(iv) prompts.ts** — replace the two "the action is ALWAYS reconnect"
passages (`:80`, `:165`) with ONE shared constant (both SOP and FIXING_SKILL
interpolate it, so they cannot drift) encoding the grounded decision table:

- Before classifying ANY auth/credential-shaped error, call
  `inspect_flow_credentials`.
- Slot unbound + `userCredentialsOfType === 0` + not system → Branch B:
  "connect <provider> in the Setup tab".
- Slot bound + oauth + (`oauthStatus` expired/needs_refresh, or auth error
  consistent with a dead grant) → Branch B: "reconnect <provider>".
- Bound id with `boundRowExists === false` → Branch B: reconnect (a fresh
  connect re-binds via server auto-bind).
- `system === true` → NEVER a user action. If `systemEnvPresent === false`,
  report a platform-side gap in one sentence (Branch P below); else treat as
  Branch A/P by evidence.
- Slot bound + healthy + auth failure → resolution layer: check call sites
  (the `prompts.ts:59` self-check — the bubble's cred must appear in
  validate_flow's required-credentials output); unrecognized call site →
  Branch A code rewrite; otherwise Branch P.
- **Branch P (platform)** — new explicit terminal: "this failure is in the
  product's credential resolution, not your account; nothing you do in the
  Setup tab will change it" + one-line layer diagnosis. Forbidden: issuing
  reconnect while inspect shows bound+active, or any user action naming a
  SYSTEM credential.

**Invariants to hold**

1. `FIX_REQUEST_MARKER` literals stay byte-identical across
   `prompts.ts:149` / `executionErrorSignals.ts:18`.
2. Page agent (`PAGE_SOP`) untouched; `AgentKind` type unchanged (importers:
   `builder.ts`, `index.ts`, `tools.ts`).
3. gluu-client stays a thin typed wrapper — no triage logic in the client, no
   `as any` (type-safety rule; the Gluu BYOC precedent).
4. Clone slots skipped via the shared `isInvocationClone` predicate — never a
   re-declared local predicate (credential-slot clone invariant, ff19891).
5. Branch-B "connect"/"reconnect" is issued only when the decision table row
   licensing it matched — the acceptance test enforces this from the thread
   transcript.

**Dead code to remove after** — the two superseded "ALWAYS reconnect"
sentences (replaced by the shared constant); nothing else becomes
unreferenced (all changes are additive; post-build re-grep
`grep -rn "reconnect" services/builder-agent/src/` must show only the
conditional decision-table text).

## 4. Event-based acceptance test (Pillar 2 — no DOM)

`scripts/event-test/s6-fixer-triage.mjs` (thin script on the F0.1 harness),
against a dev-stack (per-stack DB — never the live DB; `bun test` directly is
forbidden, memory `bun-test-wipes-live-db`). Three cases, exit non-zero on any
failed assertion.

**Case 1 — SYSTEM/platform layer (the S6 injection).** Flow using
`web-scrape-tool`/`web-search-tool` (FIRECRAWL_API_KEY is SYSTEM,
`credential-schema.ts:884`) with the API's `FIRECRAWL_API_KEY` env unset.

1. `POST /bubble-flow/:id/execute-stream` → collect SSE. Assert precondition:
   at least one signal where `bubble_execution_complete.additionalData.result.success === false`
   (the exact predicate `collectRunErrorSignals` uses).
2. `POST /build/:flowId/message` with the composed `[RUN ERROR REPORT]` body.
3. `GET /build/:flowId/thread` → assertions on `transcript[].blocks[]`:
   - `some(block => block.type === 'tool_use' && block.name === 'inspect_flow_credentials')` — grounding ran;
   - final assistant text does NOT match `/reconnect|go to the setup tab/i`
     (no impossible user action);
   - final assistant text matches `/(platform|system credential|our side|resolution)/i`
     (the layer is diagnosed).

**Case 2 — reconnect stays correct when it helps.** Seed a `GOOGLE_DRIVE_CRED`
row with a garbage refresh token and past `oauthExpiresAt`, bound to a
`list_files` flow. Assert precondition from `GET /credentials`: that row's
`oauthStatus === 'expired'`. Run → fix request → thread assertions:

- `inspect_flow_credentials` tool_use present;
- final assistant text matches `/reconnect/i` AND names Google Drive;
- no `save_flow` tool_use in the turn (a setup problem was not masked in code).

**Case 3 — missing entirely.** Flow requiring `SLACK_CRED`, zero slack rows.
Thread text matches `/connect/i` (not `/reconnect/i`) and names Slack;
`GET /credentials` confirms zero rows of the type as the precondition.

Every assertion reads: execute-stream SSE, `GET /credentials`,
`GET /bubble-flow/:id` (bound-slot precondition from `bubbleParameters`), and
`GET /build/:flowId/thread`. Nothing reads the DOM.

## 5. Risks + open questions

**Risks**

- Prompt compliance is probabilistic; mitigation is asserting the
  `inspect_flow_credentials` tool_use block (hard evidence the grounding ran),
  not only the reply text.
- `oauthStatus === 'expired'` means the ACCESS token lapsed — a live refresh
  token would recover it silently. Only combined with a runtime auth failure
  does it imply a dead grant; the decision table must require both, or the
  fixer will over-issue reconnect for healthy creds mid-refresh.
- Sequencing: S6 depends on S1. Before S1 lands, nested-tool slots are unbound
  by design, and the inspect tool would classify them "missing" (Branch B
  connect) — wrong for SYSTEM-typed nested creds; Case 1 covers the SYSTEM
  case, but the full nested-layer truth arrives with S1.
- The sidecar calls the API unauthenticated (dev DISABLE_AUTH); the new
  endpoint inherits this. Fine for dev; flag for the auth pass.
- Test seeding writes credential rows — per-stack dev DB only.

**Open questions for the user (block execution)**

1. **Branch P sign-off.** The standing rule (memory `agent-output-behavior`,
   `prompts.ts:81`) says error handling is BINARY: fix, or actionable user
   step — "explain without resolving" is forbidden. The S6 acceptance
   ("diagnoses the resolution layer", no user action) requires a third
   terminal for platform-layer faults. Approve Branch P as stated, or specify
   the wording a platform fault should surface to a non-technical user?
2. **Endpoint vs sidecar-composed.** Recommended: the new
   `GET /bubble-flow/:id/credential-state` endpoint, because SYSTEM-ness and
   platform-env presence exist only inside the API process and the sidecar has
   no shared-schemas dependency. Alternative (no API change): the sidecar
   composes from `GET /bubble-flow/:id` + `GET /credentials` and hard-codes a
   SYSTEM list — rejected here as a drift hazard. Confirm the endpoint.
3. **Scope.** The same ungrounded sentence exists in the BUILD SOP
   (`prompts.ts:80`) and in `report_missing_credential` guidance. Plan fixes
   both via the shared constant. Confirm S6 covers build-time Branch B too,
   or restrict to fix mode.
4. Should Branch P also mark the build thread (e.g. a `platform_issue` field)
   or POST `/telemetry`, so platform faults are queryable instead of living
   only in transcript prose? Additive; needs a decision.
