# Render deploy — manual steps

What's already built, in the repo: `render.yaml`, `Dockerfile.builder-agent`
(new), `GET /wake` route in `apps/bubblelab-api/src/index.ts`, and a shared-
secret gate protecting `builder-agent` (`builderAuthHeaders()` in
`apps/bubblelab-api/src/services/builder-runtime.ts`, the checking
middleware in `services/builder-agent/src/index.ts`). Everything below is
what only a human can do — Render Dashboard clicks, secret values, DNS.
Sources consulted: render.com/docs/blueprint-spec,
render.com/docs/private-services, render.com/docs/private-network,
render.com/docs/static-sites, render.com/docs/free (2026-08-13).

**Cost: $0/month.** All four resources (`bubblelab-db`, `bubblelab-api`,
`builder-agent`, `bubble-studio`) run on Render's free tier. `builder-agent`
is a public web service, not Render's genuinely private `pserv` type —
private services have no free tier (confirmed at render.com/docs/free,
cheapest paid option is $7/month). See "How builder-agent is protected"
below for what replaces that isolation.

## 1. Deploy the Blueprint

1. Push `render.yaml` to `main` (already there if you're reading this after
   the last push).
2. Render Dashboard → **New** → **Blueprint** → connect the
   `BrennanOwYong/BubbleLab` repo → Render reads `render.yaml` and shows the
   4 resources it will create: `bubblelab-db` (Postgres), `bubblelab-api`,
   `builder-agent`, `bubble-studio`.
3. Render prompts for every `sync: false` env var before the first deploy.
   Fill these in (values come from your own accounts, never from this repo):
   - `OPENROUTER_API_KEY` — the key already used locally
     (`services/builder-agent/.env`)
   - `OPENAI_API_KEY`
   - `GOOGLE_API_KEY`
   - `GOOGLE_OAUTH_CLIENT_ID` / `GOOGLE_OAUTH_CLIENT_SECRET`
   - `FIRE_CRAWL_API_KEY`
4. Click deploy. `CREDENTIAL_ENCRYPTION_KEY`, `WAKE_SECRET`, and
   `BUILDER_AGENT_SECRET` are all auto-generated by Render
   (`generateValue: true`) — you never type these.

## 2. Verify the assigned URLs match render.yaml's assumptions

`render.yaml` hardcodes `https://bubblelab-api.onrender.com`,
`https://builder-agent.onrender.com`, `https://bubble-studio.onrender.com`
(confirmed pattern per Render's docs — all service types get this address
format). Render appends a random suffix instead **only if that exact name
is already taken by someone else** — a real possibility since `onrender.com`
is a shared global namespace.

After first deploy, open each service in the dashboard and confirm its URL
is exactly what's hardcoded. If Render appended a suffix:

- Update the literal `value:` fields for `NODEX_API_URL`, `BUILDER_AGENT_URL`,
  `GLUU_API_URL`, `VITE_API_URL`, `STUDIO_URL` in `render.yaml` to the real
  assigned URLs.
- Commit, push, Render redeploys automatically.

## 3. How builder-agent is protected (read this before worrying about it)

`builder-agent` has a real public URL now, reachable by anyone who finds it
— there's no way around that on the free tier. What stops it from being
useful to anyone but your own app:

- Every route except `/health` requires an `x-builder-secret` header
  matching `BUILDER_AGENT_SECRET` (generated by Render, never in this repo).
  No header, no match → `401 {"error":"unauthorized"}`, immediately, before
  any of your data or code is touched.
- `bubblelab-api` is the only thing that knows this secret and sends it
  automatically on every call. A stranger hitting `builder-agent`'s URL
  directly gets 401s on everything — they cannot start a build, read a
  thread, or trigger anything, because they don't have the secret and
  cannot get it from the public app itself.
- `/health` stays open on purpose — Render's own platform prober hits it
  with no custom headers, and if it 401'd, Render would think the service
  is unhealthy and keep restarting it. `/health` only returns a pid/uptime
  style status, nothing sensitive.

This is application-layer protection, not network-layer isolation. The
difference: with Render's true private-service type, the URL simply
wouldn't resolve outside Render's own network — nothing to find, nothing to
probe. Here, the URL resolves and answers "unauthorized" to everyone except
your own API. For a small group of friends testing a demo, this is a
reasonable trade for staying at $0/month.

## 4. Google OAuth — register the production redirect URI

The existing dev range (localhost:3100–3130) does not cover the production
domain. In Google Cloud Console → your OAuth client → Authorized redirect
URIs, add:

```
https://bubblelab-api.onrender.com/oauth/google/callback
```

(Adjust the host if step 2 changed it.) Without this, Google Sheets/Drive
credential connect will fail with the same "doesn't comply with OAuth 2.0
policy" error seen earlier in dev.

## 5. Wire the wake trigger into your existing Telegram bot

Your bot already runs 24/7 elsewhere. Its trigger function needs to:

1. `GET https://bubblelab-api.onrender.com/wake?secret=<WAKE_SECRET>`
   - Find `WAKE_SECRET`'s generated value: Render Dashboard → `bubblelab-api`
     service → **Environment** tab.
   - This call forces `bubblelab-api` awake (the request itself wakes it)
     and pings `builder-agent`'s `/health` (with the internal
     `BUILDER_AGENT_SECRET` header, handled automatically) to wake that too.
     Response: `{"apiAwake":true,"builderAwake":true,"studioUrl":"https://bubble-studio.onrender.com"}`.
   - Times out at 60s if `builder-agent` is slow to cold-start; a `false`
     `builderAwake` on first call is expected occasionally — the bot should
     hand back `studioUrl` regardless and not block on it, since
     `bubble-studio` itself (a static site) never sleeps and opens instantly.
2. Reply to the requesting friend with `studioUrl` from the response.

Full bot-facing procedure: `PLAN-DOCS/BOT-WAKE-INSTRUCTIONS.md`.

## 6. Known gaps, not addressed by this deploy

- **Free tier cold start.** `bubblelab-api` and `builder-agent` both sleep
  after ~15 min idle (Render's documented free-tier behavior), ~30-50s to
  wake. The `/wake` call in step 5 exists to absorb this before the friend
  clicks anything, not to eliminate it.
- **No custom domain**: everything is on `*.onrender.com`. Adding one later
  is a dashboard action (render.com/docs/custom-domains) + a DNS CNAME at
  your registrar — Cloudflare DNS specifically documented at
  render.com/docs/configure-cloudflare-dns (CNAME to the onrender.com host,
  DNS-only/grey-cloud until Render issues the cert, then proxy/orange-cloud
  is optional).
- **`DISABLE_AUTH=true`**: per your choice, testers hit the app with no
  sign-in. Fine for friend-testing; revisit before any wider release.
